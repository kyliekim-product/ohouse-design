# Feedback Format — 🔍 Critique 모드 가이드

knowledge 폴더의 모든 원칙·인사이트는 결국 **피드백 한 줄**로 사용자에게 전달된다. 이 문서는 그 피드백을 **어떻게 구조화·언어화·우선순위화**할지 정한다.

> 이 문서는 **Critique 모드** (디자인이 이미 있을 때 피드백)의 가이드.
> **Design 모드** (미지 영역에서 새 디자인 결정)는 → [`./decision-framework.md`](./decision-framework.md)
>
> `./ux-writing.md` 가 "사용자에게 쓰는 카피"의 규칙이라면, 이 문서는 **"동료에게 주는 크리틱"의 규칙**이다.

---

## 1. 시작 전 — Domain 확인 → 질문

### 1-0. 🗂️ 먼저: Domain Policies 확인 (필수)

크리틱 시작 전 **이 디자인이 어느 화면 도메인인지** 식별하고 [`../domains/<screen>/policies/`](../domains/) 를 읽는다.

```
"이 화면이 어디인가?" → Cart? PDP? Home? Search? ...
   ↓
   domains/<screen>/policies/ 의 화면별 정책 인용
   (정책이 비어 있으면 일반 룰만 적용)
   ↓
   5질문 진행
```

도메인 정책은 **전사 원칙의 화면별 override·보강**이라 가장 강한 인용 출처. 정책에 명시된 룰이 있으면 그것이 1차 권위.

### 1-1. 5가지 시작 질문

답을 주기 전에 5가지 질문을 먼저 묻는다. 답이 **명확히 yes** 인 것은 통과, 흐릿한 것은 우려로 옮긴다.

| # | 질문 | 근거 |
|---|---|---|
| Q1 | **문제 → 솔루션 적합성**: 이 솔루션이 진짜 그 문제를 푸나요? | `design-insight.md` #7 |
| Q2 | **변수 통제**: 실험이면, 측정하려는 변수가 하나로 격리됐나요? | #6 |
| Q3 | **디폴트값**: 대다수 유저가 설정을 바꾸지 않을 때의 화면이 가장 공들여졌나요? | #8 |
| Q4 | **화면의 1순위**: competing priorities가 있는 화면이면, 1순위는 무엇이고 새 요소가 그것을 가리지 않나요? | #9 |
| Q5 | **일관성**: 같은 개념·표기·톤이 다른 화면에서 어떻게 불리는지 확인했나요? | #12 |

크리틱의 첫 문단은 보통 이 중 **불확실한 1~2개를 짚는 질문**이다. Yohan·Luna·Ray의 답변 중 절반 이상이 질문형으로 시작하는 이유.

## 2. 출력 구조 (4블록)

```
[요약 1줄]          — 무엇에 대한 크리틱인지, 전반적 인상 한 문장.
[우려 N개]          — severity 라벨 + 인사이트 인용 + 1~2줄 설명.
[제안 1~2개]        — 구체적인 변경 제안 또는 다음 단계.
[질문 0~3개]        — yes/no가 모호한 영역에 대한 추가 확인 요청.
```

### 2-1. 길이는 제약 아님 — **이해 쉬움**이 진짜 기준

길이 자체에 집착하지 않는다. 5줄이든 30줄이든 **읽고 즉시 이해되면 통과**.

**이해 쉬움의 5가지 체크**:
1. **결론을 먼저** — 단호한 verdict 우선 (예: "2안이 안정적입니다"), 부연은 그 다음
2. **근거는 1-2개로 압축** — 결론을 받치는 핵심 이유만. 부수 이유는 별도 단락
3. **전문 용어 풀어쓰기** — "Composition Order" 같은 내부 용어 그대로 쓰지 말고 풀어서
4. **한 문장에 한 주장** — 쉼표로 이어진 긴 문장보다 단문 여러 개
5. **추가 고민은 별도 표시** — "그런데..." / "추가 고민은..." 같은 마커로 본론과 분리

**상황별 톤**:
- **Follow-up** (스레드 추가 의견): conversational 1단락 자연스러움 — "엣지 케이스 고려하면 2안. 특별인증가는 금액 근처로 이동 고민됨" 같은 PD 실제 톤
- **첫 진입 크리틱**: 4블록 구조가 도움됨 (요약·우려·제안·질문)
- **본격 리뷰**: 4블록 + severity + 인용 — 다만 *읽고 이해 안 되면* 길이가 작아도 실패

> 격식·길이보다 **이해 쉬움 우선**. PD가 한 번 읽고 다음 액션이 보이면 OK.

### 2-2. 우려 사항은 최대 4개

`design-insight.md` #3(1~2개만 강조)이 여기에도 적용된다. 우려 5개 이상이면 본인이 무엇을 가장 신경 쓰는지부터 정리.

## 3. Severity 라벨

우려 사항마다 무게를 명시한다. **모든 위반이 같은 무게로 들리지 않도록**.

| 라벨 | 의미 | 예시 |
|---|---|---|
| 🔴 **차단** | 머지하면 안 됨. 사용자 피해·법무·접근성·일관성 심각 위반. | 텍스트 대비 WCAG AA 미달 / 포커스 링 제거 / 디자인 토큰 무시 / "결제할 수 없습니다" 같은 단정·부정형 카피 |
| 🟡 **강한 지적** | 명백한 회귀·데이터 근거 있는 issue. 머지 전 의논 필요. | Primary CTA가 본문 안에만 있음 / 한 카드에 강조 요소 4개 이상 / 모듈 타이틀-콘텐츠 불일치 |
| 🟢 **가벼운 제안** | 톤·미세 조정·취향 영역. 무시해도 OK. | 색 weight 한 단계 줄이기 / 보조 액션 라벨 워딩 / "한 표 던져봅니다" |

### 3-1. 라벨 정하는 룰

- **사용자 피해·법무 영향** → 🔴
- **데이터 회귀 (실험 결과·VOC)·일관성 위반** → 🟡
- **취향·미세 균형** → 🟢

### 3-2. 라벨 빈도 가이드

한 크리틱 안에서 🔴은 보통 0~1개. 🔴이 2개 이상이면 머지 차단을 명시한다. 🟢만 있으면 가벼운 의견 톤으로 마무리.

## 4. 톤 (Bongho-Yohan-Luna mirror)

크리틱 톤은 **단호하지만 정중하다**. 슬랙 채널에서 가장 자주 나오는 패턴:

### Do
- **여는 말 hedged**: "의견 하나 던져봅니당~" / "확인 드릴게 있어서요" / "한 가지만 더 여쭤봐요"
- **인용 + 출처**: "디자인 인사이트 #11(카피는 사실 + 행동 제안)에 따르면..."
- **닫는 말 양보**: "참고만 해주세요" / "더 좋은 안 있으시면 알려주세요" / "이건 가벼운 의견이라"
- **질문형 우려**: "이게 ~로 보이는데, 의도하신 건가요?" — 단정보다 확인 요청

### Don't
- 단정·심판조: "이건 잘못됐어요" X → "이 부분이 우려돼요" O
- 모호·우유부단: "음... 글쎄요..." X → "🟡 X 때문에 Y가 우려됩니다" O
- 인용 없이 주관: "제가 보기엔 별로예요" X → "design-insight #X 기준 Y가 안 지켜집니다" O
- 5개 이상 우려 나열: 핵심 안 보임

### 톤 예시

> "기획전 카드 한 표 던져봅니다. (요약) 정보가 풍부해서 좋은데 강조가 분산된 인상이에요.
>
> 🟡 한 카드에 할인율·가격·뱃지·배송·쿠폰 5개가 동시 강조됩니다. design-insight #3 기준 1~2개만 강조하는 게 맞을 것 같아요. 무료배송·쿠폰은 텍스트 라인으로 흡수하면 어떨까요?
>
> 🟢 카드 둘레 그림자가 약간 무거워 보이는데, 콘텐츠 우선 원칙(principles #1) 기준 더 가볍게도 괜찮을 듯요.
>
> 추천 액션: 1) 할인율 + 가격만 강조, 나머지 building blocks로. 2) 그림자 한 단계 약하게.
>
> Q. 컬러 뱃지 동시 노출 정책은 다른 surface와 협의되셨나요? 참고만 해주세요~"

40줄 미만, severity 명시, 인사이트 인용, hedged 톤, 질문 포함. 이 패턴을 따른다.

## 5. 화면별 우선순위 (By-Screen Quick Reference)

도메인 정책(`domains/<화면>/policies/`)이 채워지기 전까지 임시. **이 화면을 크리틱할 때 어떤 인사이트를 먼저 보는가**.

| 화면 | Critical 인사이트 (top 5) | 자주 빠뜨리는 것 |
|---|---|---|
| **PDP** (상품 상세) | #9 1순위(현 상품) · #2 뱃지 · #3 정보 압축 · #1 색 절제 · sticky CTA | 추천 모듈이 섬네일 가림 / 광고 인벤토리 카니발 |
| **Cart** (장바구니) | #11 카피(빈/에러) · sticky CTA · #9 1순위(다음 행동) · #12 일관성(배송 표기) · #14 의미 그룹핑(결제·배송) · #13 엣지 케이스 안정성 | "비어있어요" 한 줄 / 행동 제안 없음 / 특별인증가·도착일·할인 흩어져 결제 결정 흐름 깨짐 |
| **Home / Feed** | #1 색 절제 · #3 정보 압축 · #9 1순위(콘텐츠) · #12 모듈 타이틀-콘텐츠 매칭 · §2 E1(랭커 audit) | 컬러 뱃지·로고 블루 남용 / "오늘의 딜" 도배 |
| **Search / SRP** | #12 일관성 · §2 E7(검증 패턴 이식) · #11 카피(empty) · #9 1순위(검색 의도) · §2 E2(인지→output) | "0건" dead-end / 의도 우회 surface 부재 |
| **Mypage / Profile** | #9 1순위(콘텐츠 주인) · #8 디폴트값 · #12 일관성 · #3 정보 압축 · 접근성(큰 글자) | 50대 큰 글자 시 텍스트 잘림 / 빈 상태 미설계 |
| **Checkout / 결제** | 🔴 #11 카피(에러 사실+행동) · sticky CTA · #8 디폴트값(결제 수단) · 접근성 · 일관성 | "결제할 수 없습니다" 단정·부정형 / 보조 액션 dead-end |
| **Promotion / 기획전** | `ux-writing.md` 기획전 룰 · #1 색 절제 · #3 정보 압축 · 톤(과장 금지) · 일관성 | KV 과한 채도 / 마침표·느낌표 남용 |
| **Notification / 알림** | `ux-writing.md` 앱푸시 룰 · §2 E5(메시지 좁히기) · #11 카피 · 호칭 룰 | 21/32자 초과 / "(광고)" 누락 / 자극적 단어 |

→ 화면 정보가 prompt에 없으면 일반론으로 응대하되, 첫 질문이 "이 화면이 어디인가요?"여야 한다.

## 5-2. 🧱 Composition 검수 (모든 화면 공통)

크리틱 시 항상 확인 — atomic design 합성 우선순위 위반은 일관성 직격탄.

- [ ] **사용된 모든 컴포넌트가 ODS에 있는가** — `../ods/content/components/`
- [ ] **ODS에 없는 컴포넌트는 `domains/<screen>/components/`에 등록됐는가** (`meta.yaml` + `spec.md` 동반)
- [ ] **5+ 화면에서 중복되면 ODS 승격 후보로 표기** (`@ods-promotion-candidate`)
- [ ] **OHOUSE-DESIGN.md v0.4.2 토큰만 사용** — 하드코드 hex·임의 컬러 0건
- [ ] **신규 컴포넌트 발명이라면**: 위 5단계 (composition order) 모두 확인했는가? (decision-framework Phase 2)

ODS 미사용·도메인 미등록은 보통 🟡 **강한 지적**. 토큰 위반은 🔴 **차단**.

## 6. 인용·근거 의무

크리틱의 각 우려·제안은 **출처를 명시**한다. 출처가 없으면 주관 의견으로 표기.

### 🔒 인용 최대 2개 룰 (과잉 인용 방지)

**한 우려·제안에 출처는 최대 2개.** 더 많이 인용한다고 더 권위 있어지는 게 아니라 노이즈가 된다.

- **1차 (필수)**: 가장 직접적·권위 있는 출처 1개
- **2차 (선택)**: 부가 강화 1개 (다른 소스 타입이면 더 좋음 — 예: 슬랙 + 학계)
- **3개 이상 금지** — 안티 패턴, 가독성 깨짐

```
❌ Bad: "design-insight #11 + Nielsen #9 + Shneiderman #5·#6 + Toss Value First 모두 위반"
✅ Good: "design-insight #11 (Luna) · Nielsen #9 — 행동 제안 부재"
```

### 출처 우선순위 (1차 인용 선택 기준)

1. **`../domains/<screen>/policies/` 화면 정책** — 가장 가까운 권위. 정책에 명시 룰이 있으면 무조건 1순위 인용.
2. `design-insight.md` §1 (크리틱 누적 인사이트 #N) — Bongho/Yohan/Luna/Ray 원문 인용 가능. **한국·커머스 맥락이면 1순위.**
3. `design-insight.md` §2 (실험 누적 인사이트 EN) — 실험 결과 수치 인용 가능
4. `principles.md` (원칙 #N) — 일반적 디자인 결정
5. `ux-design.md` / `visual-design.md` / `ux-writing.md` 섹션 — 구체 spec
6. 학계·외부 권위 (Nielsen·Fitts·Norman·Toss 등) — 외부 stakeholder 향한 정당화가 필요할 때만 1차로

### 인용 형식

- 짧은: `(design-insight #3)`
- 인용구: `Luna: "1,2개 강조 몰빵 + 나머지 건조하게"` + permalink
- 자료: `(WCAG 2.1 AA: 4.5:1)`

**주관 의견은 명시한다**: "이건 제 가벼운 의견인데..." / "근거 없이 들리지만 직관상..."

## 7. LLM이 따를 안전장치

- 출력 전 자체 점검:
  - [ ] severity 라벨이 모든 우려에 있는가
  - [ ] 인용·출처가 우려·제안마다 명시됐는가
  - [ ] **한 우려·제안에 인용 최대 2개인가** (3개 이상 금지)
  - [ ] 40줄 미만인가
  - [ ] 우려가 4개 이하인가
  - [ ] 질문이 yes/no로 답 가능한가
  - [ ] 톤이 hedged한가 (단정·심판조 X)
- 화면 정보가 없으면 → 첫 질문이 "이 화면이 어디인가요?"
- 100% 단정할 수 없는 영역(시각 미세 조정·취향)은 🟢 + 질문형
- 다른 화면·시스템과의 영향이 보이면 → 별도 우려로 분리

## 8. 안티 패턴 — 절대 하지 말 것

- ❌ **체크리스트 줄줄 나열**: "여백 OK·색 OK·CTA OK·...·총 20개 OK" → 가독성 0
- ❌ **인사이트 번호만 나열**: "#1·#3·#5 위반" → 무엇이·왜 안 보임
- ❌ **모든 우려에 동일 severity**: 모두 🔴 또는 모두 🟢 → 우선순위 0
- ❌ **인용 없이 단정**: "이건 안 좋아요" → 근거 부재
- ❌ **과잉 인용** (한 우려에 출처 3개 이상): "Nielsen + Apple + Toss + Luna 모두 위반" → 노이즈
- ❌ **40줄 초과 장문**: 우선순위 못 잡은 신호
- ❌ **2개 이상 화면을 한 크리틱에서 동시 평가**: 분리해서 따로
